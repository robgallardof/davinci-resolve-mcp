# Connect your agent to Resolve Forge

One local **stdio MCP server**, `resolve-forge`, serves every client. Install the workspace once,
then configure the client on the same computer as Resolve. A generated configuration is not proof
of a live connection: verify `forge_status` from each client you use.

## Quick start

1. Run the [installer](install.md), open Resolve with a project and start the bridge in Free.
2. From the repository root run `python scripts/sync.py` (or use the bootstrap, which runs it).
3. Open this folder in your client, enable/trust the server as required and reload its MCP connection.
4. Ask: **"Read AGENTS.md and the davinci-resolve-mcp skill. Call forge_status and list_clips;
   report project, timeline, edition and transport without modifying anything."**

`config/mcp.servers.json` is the canonical launch definition. Generated files resolve the checkout's
absolute path; regenerate after moving it. They are ignored by Git and should not contain credentials.
Sync owns these generated project files; merge any additional client settings separately and keep a
backup before regenerating a file you customized. It does not edit your global client configurations.

## Client matrix

| Client | Configuration generated here | Enable/check |
|---|---|---|
| Claude Code | `.mcp.json` | Open this repository, approve project MCP; inspect `/mcp` |
| Codex | `.codex/config.toml` | Use a trusted project; inspect configured MCP servers, then call `forge_status` |
| Antigravity (current workspace support) | `.agents/mcp_config.json` | Open the workspace; inspect MCP manager and reload |
| Cursor | `.cursor/mcp.json` | Enable `resolve-forge` in the client's MCP settings |
| Gemini CLI | `.gemini/settings.json` | Open this repository and inspect MCP availability |
| VS Code with an MCP-capable agent | `.vscode/mcp.json` | Enable its MCP support and trust the workspace/server |
| Claude Desktop / other local stdio clients | Manual import | Merge the `resolve-forge` entry from generated `.mcp.json` into the client's server configuration |

Configuration generation and protocol behavior are tested locally. The table describes integration
paths, not a claim that every client/version has been tested with a live Resolve session. MCP support
and local process access are required; an ordinary cloud chat cannot start this local stdio process.

### Claude and Codex

Claude Code uses the project `.mcp.json`; Claude Desktop has a separate setup. Use Desktop's MCP
configuration workflow to merge the generated entry rather than assuming it reads this repository.
Claude's portable skills/roles are linked under `.claude/`; `CLAUDE.md` points at `AGENTS.md`.

Codex uses the generated project TOML in a trusted workspace. For user-wide setup, merge only the
`[mcp_servers.resolve-forge]` table into your user configuration; do not replace the whole file.
Open the repository so its instructions and `.agents/skills` are available.

### Antigravity

Current official documentation supports `.agents/mcp_config.json` for workspace setup. This is now
generated by sync. If your installed version requires manual setup, open **MCP Servers → Manage MCP
Servers → View raw config** and merge the generated `resolve-forge` entry into the configuration it
actually opens. Keep other server entries. Reload and call `forge_status`; do not assume older versions
use the same location. A `.gemini/settings.json` entry alone does not configure every Antigravity version.

MCP registration and instruction discovery are separate. Ask the client to read `AGENTS.md`, then the
relevant `.agents/skills/<name>/SKILL.md` and `.agents/agents/<role>.md` if it does not discover them.
If it cannot delegate, follow the role files sequentially. Only one coordinator writes to Resolve.

## Manual stdio setup

Copy the **generated** command/arguments instead of duplicating a second launch definition.
Its shape is:

```json
{
  "mcpServers": {
    "resolve-forge": {
      "command": "uv",
      "args": ["run", "--quiet", "--no-sync", "--directory", "/ABSOLUTE/CHECKOUT/mcp/resolve-forge", "python", "-m", "resolve_forge.server"],
      "env": {}
    }
  }
}
```

Replace the example path; on Windows, use forward slashes or JSON-escaped backslashes. Enter arguments
as separate array items so spaces in paths survive. Clients with a different wrapper (VS Code `servers`,
Codex TOML) should use their generated file. Forge currently does not offer a hosted HTTP/SSE endpoint;
the Free bridge port is an internal Resolve connection, not an MCP server URL.

## Diagnose the right layer

| Symptom | Next step |
|---|---|
| `uv` not found | Ensure the desktop client's environment can find uv; use its absolute executable path in that client's configuration if necessary |
| MCP exits before listing tools | Run the bootstrap/dependency setup; `--no-sync` assumes installation is already complete; inspect client server logs |
| Tools absent after sync | Check enabled/trusted workspace, actual config location and server reload; remove stale duplicate Forge definitions |
| Tools visible, `RESOLVE_UNREACHABLE` | Open a Resolve project; Free: start Workspace → Scripts → resolve_bridge again; Studio: enable Local external scripting |
| Wrong timeline | Read status and clips again before writing; clients share the same Resolve session |
| Remote/WSL/container client | It needs access to the same local runtime/Resolve bridge; this workspace does not automatically route across hosts |

Run `cd mcp/resolve-forge` then `uv run resolve-forge-doctor` for connection diagnosis.
`python scripts/sync.py --check` from the root verifies generated files, not running clients.
Avoid simultaneous edits from several clients even when they are all connected.
